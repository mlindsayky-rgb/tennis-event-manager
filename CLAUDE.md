# Tennis Event Manager

Single-file vanilla JS app: `app.html` (the main app), plus standalone `tv.html` (TV/scoreboard display), `results.html` (public results page, by league+week), and `team.html` (public, per-team schedule + league standings, by `?code=`). No build step, no framework, no package.json — just static HTML/JS served as-is.

## Deploy workflow
- Production site: https://clubeventmanager.netlify.app/ — Netlify auto-deploys from the `main` branch only (see `netlify.toml`: no build command, publishes repo root, redirects `/` to `/app.html`).
- For changes discussed and approved in chat: commit and push directly to `main`. No PR step needed (single-user project).
- For anything risky or hard to reverse (schema/migrations, auth logic, deploy config): describe the change and wait for explicit go-ahead before pushing, same as a migration.
- The user does not pull files or run terminal/deploy commands themselves — pushing to `main` is the entire deploy step; Netlify picks it up automatically.
- GitHub Pages (`mlindsayky-rgb.github.io/tennis-event-manager/app.html`) is still live in parallel as a safety net while Netlify beds in — not the deploy target, just a passive mirror of the same `main` branch. Ask before disabling it.
- `netlify.toml` sets `Cache-Control: no-cache, must-revalidate` on every page — there's no build step or cache-busting filename, so without this a browser/CDN could keep serving a stale `app.html` after a push even through a hard refresh (this happened once, mid-debugging, and cost real time misdiagnosing a "bug" that was actually just stale code). If a fix "isn't showing up," suspect this is somehow not in effect (e.g. GitHub Pages, which has no such header) before assuming the code is wrong.

## Backend
- Supabase project: "Battle Tracker", ref `vrnvhrruvzcnslvceacn`.
- Anon-key-only client, no real per-role auth — PIN-based login. Admin PIN (`admin_config`), director PIN (`directors`), coach PIN (`coaches.pin_hash` — one PIN per coach, not per team; a coach can be assigned to multiple teams, including more than one team within the SAME league), and captain PIN (`league_teams.captain_pin_hash` — a captain is tied to one specific team, not a personal account). Whether a coach lands on a Leagues picker (reusing the director screen, filtered to only her leagues) or goes straight into one league is decided by her distinct `league_id`s (`coachLeagueIds()`), never by her team count — she can have 2+ teams in one league and still only have 1 league. Once inside a league, `currentUser.teamIds` (not a single `team_id`) holds every team of hers in that league, and that's what gates roster access/ownership — a single `team_id` is kept too as a "primary" pick for the few features that only support one team (Up Next card, team-addressed messages), which is a known minor gap for a coach with multiple teams in one league (not reported as broken, just incomplete). `league_teams.coach_pin_hash` is a vestigial, unused column — pending a DROP COLUMN that's been blocked by a transient migration-tool timeout (harmless to leave; nothing reads it).
- Role hierarchy: admin > director > coach > captain (> player). Role gating is UI-only (hiding nav/buttons) — RLS is enabled on tables but with permissive `allow_all` policies for `anon`/`authenticated`, so it is not a real per-role security boundary. Treat it accordingly: don't assume RLS protects anything a determined client couldn't bypass.
- A director's global Players directory (`dir-nav-players`, `loadPlayers`) is filtered by `player_clubs` — a many-to-many table, separate from `players.home_club_id`. Every place that sets `home_club_id` must also upsert the matching `player_clubs` row (`{onConflict:'player_id,club_id', ignoreDuplicates:true}`), or a player ends up with the right home club on file but stays invisible in every director's directory anyway. This shipped three times before all known spots were covered — `backfillPlayerHomeClub` (single roster-add), the bulk roster import, `savePlayer` (the Players directory's own "+ Add Player", which now also auto-assigns a director's own club), and `saveMissingDataField`'s `home_club_id` case. The one actually-correct way to manage club membership directly is the 🏛 icon's `togglePlayerClub` (writes `player_clubs` only) — don't follow `home_club_id`-only code as a model for a new call site. One-time data backfills fixed the live players each round of this had already hit.
- A director's Leagues list (`loadLeagues`) is filtered to leagues where their own club (`currentUser.club_id`) has at least one team — not every league system-wide. Two clubs sharing a league (their teams play each other) see that one league from both sides; this is visibility only — once inside a league, a director still has full staff access to everything in it (add team, settings, etc.), including a shared one. Restricting that further to just their own club's team is a deliberately separate, not-yet-decided question — don't assume it's covered.
- "Derive, don't store" — rankings and schedules are computed live from matches/results, not cached columns.
- Core tables: `clubs`, `directors`, `players`, `coaches`, `leagues`, `league_teams`, `league_team_players`, `league_matches`, `court_results`, `league_sub_pool`, `league_interested_subs`, `messages`, `message_recipients`, `app_settings`, `admin_config`.
- `coaches` is a shared directory (name/phone/email), linked from `league_teams.coach_id` — a coach is one record, editable from the team modal or the admin/director "Coaches" tab, and edits propagate to every team that coach is linked to. Picking/typing a coach name in the team modal matches against this table before creating a new row, to avoid duplicates/typos.
- `players.home_club_id` auto-fills from a team's assigned club when a roster is loaded (bulk upload or single add) — backfill-only, never overwrites a club a player already has.
- Missing Data tooling (admin, director, and the coach-facing per-league tab — not captain) flags players missing last name / phone / home club, defaults to showing only players added in the last 45 days.
- League scheduling (`seasonWeekDates`/`isMatchWeek` in `app.html`): a league's Dates Off cause that calendar week to be skipped entirely (no match, no practice), extending the season by a week to make up the meeting count. Practice/match alternation always follows the actual, compacted meeting order — never the raw calendar date — so a skipped week never produces two of the same type in a row. `leagues.start_with_match` (league modal checkbox, only shown/relevant when alternating is on) flips which parity is the match: off (default) is week 1 practice/week 2 match as always; on is week 1 match/week 2 practice. Dates Off skipping is unaffected either way — it only decides which calendar weeks get skipped, not which compacted week is which type. `team.html` carries its own copy of `isMatchWeek`, kept in sync with `app.html`'s.
- End Date auto-fill: start date counts as week 1 day 1, so N weeks lands N×7-1 days out; each Date Off adds one bonus week. No day-of-week rounding.
- `league_teams.team_code` (unique, random 6-char hex, set at team creation) is a no-login shareable link for players — `team.html?code=XXXXXX` shows that team's own schedule (practice/match weeks, opponent, result once entered) plus the whole league's standings. Editing a team shows/copies/regenerates its link. This is intentionally simpler than the existing personal player PIN login (`players.pin_hash`, the full `player-screen`) — the team code needs nobody to remember a PIN, it's just "do you have the link," and stays read-only.
- Standings everywhere a player name is shown to the public (currently just `team.html`) use "First L." (first name + last initial) — a player missing a last name (the same single-word-name condition the admin Missing Data tool flags) shows as "First &." instead of guessing or showing a bare first name.
- `results.html` still carries an OLD, un-fixed copy of `seasonWeekDates`/`isMatchWeek` (no Dates-Off-skip, the pre-fix rounding math) — `team.html`'s copy is the current, correct one. If `results.html` is touched again, port the same fix into it; don't assume it already matches `app.html`.
- "Events" (`events`/`teams`/`team_players`/`event_players`/`rounds`/`pairings`/`scores`) is a separate one-day feature from Leagues — a team-vs-team "Battle" format: `num_teams` balanced teams (snake-draft by gender/rating), rounds that rotate which team plays which, doubles partnerships formed within each team per round. Its pairing engine fundamentally requires 2+ teams (`matchups` are built by pairing teams against each other) — it cannot represent one pooled group with no fixed teams; that would need a different algorithm, not a config change. A Leagues-side "Round Robin" league type spanning multiple weeks (pooled roster, rotating partners, no fixed teams) was considered and paused for now — Events' single-day format is what's actually in use.
- Events has an individual-player Standings tab (`computeEventStandings`/`loadEventStandings`, event-nav "Standings") — win %, games %, W-L per player across the whole event, derived from `pairings`+`scores`, same derive-don't-store pattern as the Leagues Player Rankings. Team is shown for reference only, doesn't affect the ranking. Every ACTIVE `event_players` row is seeded at 0-0 even with no courts played yet; INACTIVE players are excluded entirely.
- A Mixer event's Rounds tab has a "Use pairing rules" toggle (`toggleMixerPairingRules`, stored as `events.round_configs.mixerRandomPairs` — a flat key alongside the per-round-number keys Battle events use in that same JSONB column, no migration needed). On (default) keeps gender/rating-aware pairing (format `BG`). Off uses format `ANY`, which falls through `buildTeamPairs` to its no-gender-filter branch — same repeat-partner avoidance as every other format, just no constraint on who's eligible, so the only guarantee is a new partner each round. `buildTeamPairs` takes an explicit pair-cap parameter (defaults to the old implicit `courts`, which is still correct for a team-vs-team call) because the Mixer single-pool call needs `courts*2` pairs, not `courts` — don't reintroduce that cap bug if this function grows another caller.
`event_type` has a `MIXER` value (added via migration) — one pooled roster, everyone plays everyone, no real teams. Creating a Mixer event auto-creates TWO hidden placeholder `teams` rows: the real pool team ("All Players", holds the whole roster via `team_players`) and an always-empty ghost (`MIXER_GHOST_TEAM_NAME`, a constant). Both are required — `pairings` has a live-schema CHECK (`different_teams`: `team_a_id <> team_b_id`) that a single shared team would violate, which is exactly the bug that shipped once (every mock test passed; every real deploy 400'd, since the mock harness had no equivalent constraint until this was added to it). `deployRound` self-heals a missing ghost team at deploy time, so an event created before this fix recovers on its next deploy with no manual data fix. Status is set straight to `TEAMS_SET` on creation — there's no Team Builder step (that nav tab is hidden for Mixer) and no num_teams. `deployRound`'s per-round pairing engine filters the ghost team out before computing `uniqueTeams`, so `uniqueTeams.length===1` still correctly means "this is the Mixer pool," and branches: pairs are built from the whole active pool at once (partners rotate every round through the existing repeat-avoidance logic) and matched against each other by closest strength, instead of splitting into two team pools and matching across them. The per-round "who plays" quota is doubled for a pooled team (it fills both sides of every court, not one). Every place that needs to know "is this a Mixer pairing/round" checks `currentEvent.event_type==='MIXER'` directly — NOT team id comparisons, which don't hold now that the two sides are different teams. That's how the round list drops team-name/color framing in favor of player-pair names, and how the RD Override "move players between courts" tool allows any-to-any swaps instead of restricting to same-side. TV Preview shows the pool team's name on both sides rather than the ghost's technical name — still not a real team-vs-team score, a known cosmetic gap. A true multi-week "Round Robin" league type (inside Leagues, not Events) was discussed and paused in favor of this — Mixer only supports single-day events.

## Testing
- Before shipping a schedule/roster/data-model change, write a Playwright test against a mock Supabase client (intercepts the `supabase-js` import and stubs `window.__mockDB`) and run the existing regression suite alongside it — this has repeatedly caught real bugs (date math, alternation logic, dedup) before they reached production. These test files are scratch work, not checked into this repo.
- Mock-vs-live-schema drift is a recurring bug class here: app-level JS validation can be correct while the live Postgres schema still rejects the data (a stale CHECK or NOT NULL constraint). When something "should work" but doesn't, check the live schema directly (`list_migrations`, `execute_sql`) before trusting the client-side code.
